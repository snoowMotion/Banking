# Budget tenable : notes pour Claude

Application de budget auto-hébergée (voir `docs/SPEC-budget-sync.md`, la spec, et `docs/reference/budget-tenable-reference.html`, le prototype qui fait foi pour les calculs).

- Stack : .NET 8 (minimal API, EF Core + SQLite), frontend JS vanilla dans `web/` (PWA). Interface et libellés en français.
- `src/BudgetTenable.Core` : calculs purs (périodes, enveloppe, pots, règles, parseurs CSV/OFX). `src/BudgetTenable.Api` : API, auth PIN, base. `tests/` : xUnit.
- Commandes : `dotnet test` ; `node --check web/app.js` ; `node tests/reference/prototype-oracle.mjs` (valeurs de référence du prototype).
- Argent : `decimal`, jamais de flottants. Dates de période en `DateOnly` (Europe/Paris), jamais en UTC.
- Les calculs de l'onglet Budget existent deux fois : `compute()` dans `web/app.js` (simulation instantanée) et `BudgetCalculator` en C# (source de vérité). Les modifier ensemble.
- Ne jamais journaliser d'IBAN ni de montants au niveau INFO. Secrets hors dépôt.
- Migrations : `dotnet-ef migrations add <Nom> --project src/BudgetTenable.Api --output-dir Data/Migrations`.
- Collage d'opérations : `PastedStatementParser` (Core) + `PasteEndpoints` (aperçu puis validation) ; rapprochement partagé avec l'import CSV/OFX dans `Reconciler`. Les correspondances catégorie bancaire -> catégorie sont dans `BankCategoryMapping`.
- Charges fixes : une charge est « payée » s'il existe une opération classée dedans dans la période (`FixedLine` dans `PeriodSummary`). Le clic crée une saisie manuelle (`FixedEndpoints`) sur `Category.AccountId` ; le rapprochement la fusionne avec la ligne bancaire collée.
- Budget daté : `BudgetTimeline` (Core) donne, pour une période, les catégories actives et leurs valeurs (`Category` = valeurs de départ + `ActiveFrom`, puis `CategoryTerm` / `IncomeTerm` à partir d'une période). `PUT /api/budget` pose un changement « à partir de P » ; tout calcul de période passe par la timeline, jamais par les valeurs brutes de `Category`. `CategoryEndpoints` : créer, renommer, arrêter, réactiver, fusionner, supprimer.
- Synchro bancaire (phase 2) : `BankFeed` (Core) traduit les opérations Enable Banking et attribue les identifiants (`eb:` + `entry_reference`, sinon `ebf:` + empreinte ; jamais `transaction_id`, qui change). `EnableBankingClient` + `EnableBankingAuth` (JWT RS256) dans `Api/Banking`, `BankSyncService` (une connexion = une session ; lecture paginée tant qu'une `continuation_key` revient, même après une page vide), `BankSyncWorker` (toutes les 6 h : limite bancaire de 4 lectures par jour sans l'utilisateur), `BankEndpoints`. `/api/bank/callback` est le seul endpoint public, protégé par un `state` à usage unique. `TransactionIngestor` est partagé avec l'import CSV/OFX ; en synchro, `Reconciler` adopte les opérations collées ou importées (`Adoptable`). La durée du consentement se lit dans `maximum_consent_validity`, jamais en dur. Tests : `ApiBankSyncTests` (fausse API `FakeEnableBanking`), `BankFeedTests`.
- État : phases 1 et 2 codées (voir README). La phase 2 n'a jamais tourné contre la vraie API Enable Banking : toute correction doit repartir de leur doc officielle (https://enablebanking.com/docs/api/reference/ et /docs/faq), pas de suppositions.
